## 7. Failure-to-run alert design

A missed-run alert must mean something stronger than “a node threw an error.”

The system must distinguish:

- **source failure:** workflow ran, but one or more upstream sources failed;
- **validation failure:** workflow ran but rejected bad output;
- **degraded/LKG:** workflow ran and safely served cached or partial data;
- **workflow execution failure:** workflow started and ended unsuccessfully;
- **missed run:** the workflow never produced current-cycle execution evidence;
- **release failure:** source cycle ran but did not reach a verified public production release;
- **platform failure:** n8n, Hetzner, GitHub, or Cloudflare failed badly enough that the internal alert path could not run.

### 7.1 Internal current-cycle completeness check

Lane 20 must inspect the expected source-lane cycle and record, for each Lane 01–08:

- expected cycle (`03:00` or `13:00`);
- latest run ID;
- execution/report timestamp;
- final report-out status;
- whether it ran inside the current cycle window;
- whether it published a valid current artifact;
- whether LKG was used;
- last known successful run time if the current run is missing or failed.

If a lane has not produced valid current-cycle execution evidence by the Lane 20 cutoff, Lane 20 must mark that lane `MISSED_RUN` in system health and send an operator email.

Recommended email subject:

```text
UW-Issy Monitor FAILED TO RUN — 03:00 cycle
```

or

```text
UW-Issy Monitor FAILED TO RUN — 13:00 cycle
```

The body should include:

- missed lane(s);
- expected cycle time;
- last known run time;
- last successful run time;
- last run status if one exists;
- age of current published/LKG data;
- Lane 20 run ID;
- n8n URL;
- public site URL.

A lane-level missed-run email is an **operations alert**, not a rider/event alert, and must not share Lane 30's event dedup state.

### 7.2 External dead-man watchdog

An internal n8n-only watchdog is not sufficient because it cannot send mail when n8n itself is down.

Use an independent external heartbeat/dead-man service.

The final successful step of each production cycle sends one heartbeat only **after Cloudflare production verification passes**.

Expected heartbeats:

- morning cycle: after the 03:00 source cycle and production release;
- afternoon cycle: after the 13:00 source cycle and production release.

Use a grace window of roughly **45–60 minutes after the expected completed release**, not merely after source-lane start time.

If the heartbeat is not received, the external service sends email independent of n8n.

This catches failures such as:

- n8n host down;
- n8n scheduler stopped;
- source workflows never started;
- Lane 20 never ran;
- Hetzner lost network;
- repository update failed;
- GitHub Actions did not run or failed;
- Cloudflare deployment failed;
- production verification failed;
- the full chain stopped before the success heartbeat.

### 7.3 Heartbeat success definition

Do **not** send the heartbeat when:

- a source lane merely starts;
- Lane 20 starts;
- Lane 20 writes `status.json`;
- GitHub receives a commit;
- GitHub Actions merely starts;
- Cloudflare deploy reports success without production validation.

Send it only after the public deployment passes the production verifier.

This makes the heartbeat statement precise:

> The scheduled UW-Issy monitoring cycle made it from source checks through a verified live public site.

## 8. Lane 01 stable event identity fix

This is a hard gate before Lane 30 activation.

### 8.1 Defect

The current long-running Route Conditions closure can receive a new event ID when the source page body or content hash changes, even if the real-world closure is the same event.

That defeats Lane 30 duplicate suppression.

### 8.2 Required identity rule

`event_id` must identify the real-world event, not the current byte content of its source page.

Use stable source/event fields such as, in priority order:

1. official stable source event ID when present;
2. source namespace + event type + stable facility/route segment + effective start;
3. another documented deterministic stable key based on real event identity.

A content hash may remain as provenance/change evidence, but it must not make the same ongoing event become a new identity.

### 8.3 Required regression tests

Before deployment of the fix:

- same closure + changed page text → same `event_id`;
- same closure + changed `last_verified_at` → same `event_id`;
- same closure + changed content hash → same `event_id`;
- genuinely new closure → new `event_id`;
- two distinct simultaneous closures → two distinct IDs;
- existing event plus new second event → Lane 30 alerts only for the new event;
- repeated run with no new real event → no email.

The fix must not erase useful provenance or source-change data.

1. Lanes 01–08 run.

15. Current valid Lane 20 snapshot enters the GitHub release input path.
16. Meaningful validated change is committed/pushed according to the selected no-op policy.
17. GitHub Actions checks out the repo and installs from the lock file.
18. Canonical GPX existence and validity are checked.
19. GPX is converted to route GeoJSON.
20. Route GeoJSON is validated.
21. Public monitoring package is built from the current Lane 20 snapshot.
22. Public package is validated, including cross-file/release-ID checks.
23. Unit tests run.
24. Typecheck runs.
25. Astro build runs.
26. Required built assets are checked.

28. Cloudflare Pages deploy runs.
29. Production verifier checks the live deployment.

31. Only after production verification passes is the external success heartbeat sent.

A production cycle is not complete merely because n8n ran or CI was green. It is complete when the live production site has passed its production checks, or when a documented no-op policy has verified that the existing live release remains valid and the cycle has still emitted its success heartbeat.

## 17. Rollback and failure rules

### 17.1 General rule

Do not destroy the last known good workflow, artifact, or site release merely because a new cycle fails.

### 17.2 Workflow rollback

Before each workflow mutation:

- export the live version;
- record live workflow ID and version/name;
- preserve the prior local canonical JSON;
- make targeted changes;
- static-validate;
- update live workflow in place where safe;
- run controlled execution;
- read real output back;
- roll back if the new version cannot meet its gate.

### 17.3 Site rollback

A failed monitoring/public-package validation must not publish bad data.

A failed CI/build/deploy must not be represented as a successful current release.

Cloudflare's prior valid deployment remains the fallback until a new deployment passes production verification.

### 17.4 Alert rollback

If Lane 30 begins sending duplicates:

- disable Lane 30 schedule immediately;
- leave source monitoring and Lane 20/site publishing running;
- preserve alert state/evidence;
- correct event identity/dedup logic before reactivation.

### 17.5 Watchdog failure

If the external heartbeat provider itself is down, record that state separately. Do not treat a watchdog-provider outage as proof the UW-Issy monitor failed. The runbook must contain a direct production-verification path independent of the heartbeat service.
