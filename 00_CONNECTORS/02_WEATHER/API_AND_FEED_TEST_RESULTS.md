# API_AND_FEED_TEST_RESULTS.md — Lane 02_WEATHER

All tests below were executed directly by command-line HTTP request (`curl`) on
2026-07-29 against live public endpoints, using the required NWS User-Agent format:

```
User-Agent: (BTF-UW-Issaquah-Weather-Research, john@biketourfrance.net)
```

Sanitized JSON samples are saved under `sample-responses/` for each test (full
per-point `/points` responses, station lists, one full forecast/hourly/

(see `README.md` "Known cleanup item") — captured before that redundancy was

**Finding — important implementation detail:** the raw GPX-derived coordinates
(5 decimal places) are NOT accepted directly; the API always issues an HTTP 301
redirect to a canonicalized 4-decimal-place coordinate. A production fetcher
**must follow redirects** (`curl -L` / `fetch` with `redirect: "follow"`) or every
request will silently fail to resolve. This matches the documented NWS caching
guidance that grid coordinates should be cached per canonical point, since the
API itself defines the canonical point via this redirect.

Response content type: `application/geo+json` (200 status); `application/problem+json`
on the initial 301 (not an error — this is normal redirect behavior with the
`Accept: application/geo+json` header set).

**Fields extracted per point (all 8 confirmed present and populated):**
`gridId`, `gridX`, `gridY`, `cwa`, `forecastOffice`, `forecast`, `forecastHourly`,
`forecastGridData`, `observationStations`, `forecastZone`, `county`,
`fireWeatherZone`, `timeZone`, `radarStation`.

**Result:** all 8 points resolve to `gridId: SEW` (NWS Seattle/Tacoma Forecast
Office), confirming the entire route sits inside a single WFO's area of
responsibility — no cross-office handoff logic is needed. `county` is `WAC033`
(King County) for all 8 points. `forecastZone` varies: `WAZ315` (WP1, WP2),
`WAZ313` (WP3), `WAZ314` (WP4–WP8). `fireWeatherZone` varies: `WAZ654` (WP1),
`WAZ657` (WP2–WP8). `timeZone` is `America/Los_Angeles` for all 8 (relevant for
`generatedAt`/local-time normalization in a future connector).

## 2. 7-day/12-hour forecast — `/gridpoints/{office}/{x},{y}/forecast`

Tested HTTP status for all 8 resolved gridpoints: **all returned HTTP 200.**

Full payload captured for WP1 (`SEW/126,70`) — see `sample-responses/WP1_forecast.json`.

- `properties.units`: `"us"` (imperial; a `?units=si` query parameter is
  documented by NWS to request SI units on this same endpoint — not indepedently
  tested this cycle, noted for implementation).
- `properties.generatedAt`: `2026-07-29T06:34:07+00:00` — timestamp of this
  specific API response.
- `properties.updateTime`: `2026-07-29T06:26:57+00:00` — timestamp the underlying
  forecast product was last generated by the forecaster/model. **This is the
  correct field for forecast-freshness checks**, not `generatedAt` (which only
  reflects when this HTTP response was built, effectively always "now").
- `properties.validTimes`: an ISO-8601 interval (`2026-07-29T00:00:00+00:00/P8DT1H`)
  giving the total forecast coverage window.
- 14 forecast periods returned (day/night pairs, ~7 days).
- Period fields: `number`, `name`, `startTime`, `endTime`, `isDaytime`,
  `temperature`, `temperatureUnit`, `temperatureTrend`, `probabilityOfPrecipitation`
  (object with `unitCode`/`value`), `windSpeed` (string, e.g. `"2 mph"`),
  `windDirection` (compass string), `icon` (URL), `shortForecast`,
  `detailedForecast` (full prose).

**Missing-data behavior observed:** `temperatureTrend` was `null` in the sampled
period — NWS returns explicit `null` for fields with no applicable value, not a
missing key. A parser must null-check rather than assume key presence implies a
value.

## 4. Raw gridpoint forecast data — `/gridpoints/{office}/{x},{y}`

All 8 gridpoints: **HTTP 200.**

Full payload captured for WP1 — see `sample-responses/WP1_gridData.json`.

This endpoint returns numeric, unit-tagged, time-series data (not prose) — the
correct source for a normalized/thresholded connector rather than parsing
`detailedForecast` strings. Confirmed present and populated (non-exhaustive,
fields directly relevant to the Connector 02 scope):

| Field | Unit (`uom`) | Confirmed present |
|---|---|---|
| `temperature` | `wmoUnit:degC` | Yes |
| `dewpoint` | `wmoUnit:degC` | Yes |
| `maxTemperature` / `minTemperature` | `wmoUnit:degC` | Yes |
| `relativeHumidity` | `wmoUnit:percent` | Yes |
| `apparentTemperature` | `wmoUnit:degC` | Yes (heat-index/wind-chill-equivalent "feels like") |
| `heatIndex` | `wmoUnit:degC` | Yes (key present; present as null when not applicable — cool-weather sample) |
| `windChill` | `wmoUnit:degC` | Yes (key present; same null-when-inapplicable pattern) |
| `windDirection` | `wmoUnit:degree_(angle)` | Yes |
| `windSpeed` | `wmoUnit:km_h-1` | Yes (raw numeric, unlike the string-formatted value in §2/§3) |
| `windGust` | `wmoUnit:km_h-1` | Yes |
| `skyCover` | `wmoUnit:percent` | Yes |
| `weather` | array of coded objects (`coverage`, `weather`, `intensity`, `visibility`, `attributes`) | Yes — this is the correct field for thunderstorm/fog/snow/freezing-rain phenomenon codes, not free text |
| `probabilityOfPrecipitation` | `wmoUnit:percent` | Yes |
| `quantitativePrecipitation` | `wmoUnit:mm` | Yes |
| `iceAccumulation` | `wmoUnit:mm` | Yes (key present, zero-valued in sample) |
| `snowfallAmount` | `wmoUnit:mm` | Yes |
| `snowLevel` | (elevation, `wmoUnit:m`) | Yes — useful for the Issaquah-foothills point (WP8) to judge rain/snow line relative to route elevation |
| `ceilingHeight` | `wmoUnit:m` | Yes |
| `visibility` | `wmoUnit:m` | Yes |
| `probabilityOfThunder` | `wmoUnit:percent` | Yes |
| `hazards` | array | Yes (key present, empty array in the clear-weather sample tested — see §6 for a populated example from elsewhere in WA) |

Each field is a **time-series array** of `{validTime, value}` objects, where
`validTime` is an ISO-8601 interval (start/duration, e.g.
`"2026-07-29T00:00:00+00:00/PT1H"`), not a single timestamp — a parser must
expand these intervals to build an hourly/period-aligned series. Interval
lengths vary field-to-field and even period-to-period within the same field
(observed `PT1H`, `PT2H`, `PT6H`, `P1DT6H` durations in the same payload) —
this is normal NWS grid behavior (longer-range periods are coarser), not a
data-quality defect.

## 5. Observation stations — `/gridpoints/{office}/{x},{y}/stations` and `/stations/{id}/observations/latest`

All 8 gridpoints' station-list endpoints: **HTTP 200**, 73 stations returned per
point (same underlying regional station list each time, ordered by the API's own
internal proximity heuristic to the gridpoint — see finding below).

**Finding — station-list ordering is not simple linear distance from the input
coordinate.** The API's returned station order was cross-checked against true
haversine distance from each WPx's exact input lat/lon. `SEAW1` (the NWS Seattle
office's own Sand Point sensor) is returned first for most points and is in fact
the closest by true distance for WP1–WP7, but `KBFI`/`KPAE`/`KRNT`/`E6690` ranks
shift point-to-point in ways that only line up with true distance, not with any
simpler heuristic — recommend a production fetcher always compute true distance
from the returned station list rather than trusting API result order alone
(computed distances are recorded per point in `ROUTE_WEATHER_POINT_MAPPING.md`).

**Latest-observation field test**, `GET /stations/{id}/observations/latest`,
run against the 4 stations recommended in the observation-station set:

| Station | HTTP | `timestamp` | `textDescription` | `temperature` | `windSpeed` | `windGust` | `visibility` | `rawMessage` |
|---|---|---|---|---|---|---|---|---|
| `SEAW1` | 200 | 2026-07-29T06:30:00+00:00 | *(empty)* | 17.22°C, `qualityControl: "V"` | 11.27 km/h | *(null)* | *(null)* | *(empty)* |
| `KBFI` | 200 | 2026-07-29T06:45:00+00:00 | "Clear" | 18°C, `V` | 5.54 km/h | *(null)* | 16093.44 m | *(empty in sample)* |
| `KRNT` | 200 | 2026-07-29T06:50:00+00:00 | "Clear" | 18°C, `V` | 7.42 km/h | *(null)* | 11265.41 m | *(empty in sample)* |
| `KPAE` | 200 | 2026-07-29T06:45:00+00:00 | "Clear" | 14°C, `V` | 9.25 km/h | *(null)* | 16093.44 m | *(empty in sample)* |

**Finding — `SEAW1` is a limited-field station.** It returns `temperature` and
`windSpeed` with a valid quality-control flag, but empty `textDescription` and
null `visibility`/`rawMessage` — it is not a full METAR-reporting ASOS/AWOS
station. `KBFI`, `KRNT`, and `KPAE` are full airport ASOS stations with
`textDescription` populated (confirms they are genuinely METAR-sourced), though
`rawMessage` happened to be empty in these specific samples (observed as an
intermittent field, not guaranteed populated every observation cycle — do not
assume `rawMessage` is always present). `qualityControl: "V"` ("verified" per
NWS's standard QC code set) was present on every temperature reading tested —
**a production fetcher should check this field and treat non-`V` codes (e.g.
`"S"` subjective, `"Z"` no QC applied) as lower-confidence,** though a full QC
code table was not independently retrieved this cycle (flag for implementation
time, see `SOURCE_GAPS.md`).

**Missing-data / stale-observation behavior:** not directly observed this cycle
(all 4 stations returned fresh, populated observations at test time — see
timestamps above, all within the same hour as the request). Documented NWS
behavior (from the API's own JSON Schema, not independently re-tested here) is
that a field with no valid reading returns `{"value": null, "unitCode": ..., "qualityControl": null}`
rather than omitting the key — consistent with the null-field pattern already
confirmed in §2 and §4.

**Overlap note (per work order Connector 02 scope rules):** the only live alert

Lane 03's primary responsibility, not Lane 02's. This is a real, confirmed
example of the documented overlap: weather-originated alerts (NWS-issued) can
carry an `event` type that belongs to another lane's primary responsibility.
Recommend Lane 02's alert ingestion filter on NWS alert `event` values that are
genuinely meteorological (e.g. Winter Storm Warning, Wind Advisory, Dense Fog
Advisory, Severe Thunderstorm Warning, Excessive Heat Warning, Freeze Warning)
and explicitly exclude/pass through Air Quality Alerts and Fire Weather
Watches to Lanes 03/04 rather than duplicate them — see `SOURCE_GAPS.md`.

## 7. Response headers — caching, rate limiting

From a live `GET /gridpoints/SEW/126,70/forecast` response:

```
cache-control: public, max-age=1556, s-maxage=3600
expires: Wed, 29 Jul 2026 07:34:07 GMT
last-modified: Wed, 29 Jul 2026 06:26:55 GMT
access-control-allow-origin: *
access-control-expose-headers: X-Correlation-Id, X-Request-Id, X-Server-Id
x-correlation-id: f7d807cb
```

**No `X-RateLimit-*` headers were present** on any tested response. Per the
official NWS API documentation (`weather.gov/documentation/services-web-api`,
fetched directly this cycle): a rate limit exists but the specific numeric
threshold is not publicly disclosed ("allows a generous amount for typical
use"); exceeding it returns an error, retriable after approximately 5 seconds;
a descriptive `User-Agent` is the required identification mechanism (not an
API key, though the docs note this "will be replaced with an API key in the
future"); grid coordinates may be cached client-side but should be periodically
re-validated via `/points` since `gridX`/`gridY`/office can occasionally change;
the API is described as using "a cache-friendly approach" and all data is
"open data, free to use for any purpose." **No rate-limit number, quota, or
SLA is claimed in this document beyond what is stated above** — per the work
order's instruction not to claim an undocumented guarantee.
